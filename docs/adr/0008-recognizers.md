# Recognizers are TOML rule files over the screen tree, and fail closed

Status: accepted, 2026-10-20. Records the grilling of [#313](https://github.com/flotilla-org/cleat/issues/313) (rulings 1–3) and the outcome ruling on [#310](https://github.com/flotilla-org/cleat/issues/310). Built in [#349](https://github.com/flotilla-org/cleat/issues/349); the format reference is [docs/recognizers.md](../recognizers.md).

Clients such as Flotilla and Wheelhouse need to know what an agent's screen means, for example whether the composer is empty, the agent is working, or a dialog is up. Each one used to scrape the screen itself. Cleat already builds a region tree with CSS-like selectors (#316) and exposes it (#24). A **recognizer** adds meaning on top: per-application rules that place role nodes (`composer`, `status`, `dialog`) in that tree, so clients ask for `composer[value='']` instead of re-implementing a classifier.

## Decision

1. **A recognizer is a TOML file of rules.** Metadata is plain top-level keys (`id`, `revision`, `min_engine`, `verified`). Each `[[rule]]` pairs a #316 selector string (`select`) with flat declarations: `role`, `state`, `kind`, and `value` filled from named captures. There is no new declaration syntax. A CSS-style stylesheet was rejected because it needs its own declaration parser and a separate metadata header. Andamento's predicate grammar was rejected because its equality-only, index-served predicates are built for fact lookup, not screen geometry. A Rust trait covers what the rules can't express, and produces the same nodes.
2. **Rules don't cascade.** Every rule sees the same unannotated input tree, never another rule's output. Rules run in file order and matches in document order; the last matched state wins. Within a rule, declared regions win over inferred ones.
3. **Selection is explicit.** A session names its recognizer at launch (`--recognizer <id>` or the tag `recognizer:<id>`). Cleat never guesses from the command line. Bundled recognizers are embedded in the binary. A same-id add-on in the add-on directory overrides the bundled file, and a broken add-on fails rather than falling back.
4. **Unknown is explicit.** A role that no rule established is absent, never assumed empty. An evaluation error discards the whole observation for that frame and shows in `inspect`. Recognizer errors and panics never block unguarded sends.
5. **Recognizers feed program status, but don't override it.** Recognizer and title state enter the same record store as OSC 7501 (ADR 0007 rule 2), tagged `recognizer` or `title`, with the root id. In what attach emits, a program's own reports still win until the program ends (ADR 0007 rule 6). Letting a recognizer override a program's reports stays **deferred**. Nothing on the current path needs it: consumers arbitrate from the store, and `composer[value]` has no OSC 7501 equivalent. Revisit it if a harness is seen sending wrong or stale 7501 while the recognizer is right.
6. **Guards distinguish "not now" from "can't know".** `cleat send --if SELECTOR` (#310) refuses with exit 1 / HTTP 409 when the selector doesn't match, when a recognizer is active but establishes no such role (`role-absent`), or when the controller is active. Callers should retry. It reports `unsupported` (exit 2 / HTTP 422) when the session has no VT engine, or when the selector names a role that no active source can produce. That is decided from the selector and the session's sources, before any screen state is read, and callers should fall back. Selectors on plain structure never need a recognizer.
7. **Every recognizer is tested against recorded casts.** Each one ships fixtures under `recognizers/fixtures/<id>/`: asciicast recordings with expected roles at named markers, recorded from the real harness and checked for private data before commit. A recognizer declares the harness versions it was verified against. A harness release that moves its composer fails a fixture, not a live delivery.

## Consequences

- Agent harnesses that report their own status (Claude Code 2.1.303 emits OSC 7501) need recognizers mainly for composer content. Harnesses that don't (Codex) depend on them for status too.
- Rules can be translated mechanically from herdr's manifests, with attribution. Herdr's structure (regions hard-coded per agent, process sniffing, unsigned network updates, defaulting to idle) is deliberately not copied.
- Without cascading or priorities, rule authors order rules deliberately. If ordering stops being enough, a later format revision can add explicit priority.
- Recording turn-dependent states needs a signed-in harness. Crew containers can't provide one to a nested instance, so those casts are recorded on a host where the harness is already signed in, with a stricter privacy pass.
- ADR 0007's "decided when recognizers land" item is answered by rule 5: still deferred, with a stated trigger.
