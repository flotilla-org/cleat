# Zellij retained Kitty assets: local source investigation

Investigated 2026-09-17 for cleat #206. Source checkout: `/Users/robert/dev/zellij`, HEAD `d262df58ebdea2549666a5060663d017545bb5cb`. Links below point to the inspected local sources.

The useful separation is between producer upload acceptance, retained asset ownership, and delivery to each terminal. These are three different lifetimes.

## Producer acceptance and retained representation

The parser accepts direct bytes, regular files, temporary files, and shared memory, including byte offset/size metadata. On completion it obtains owned image data, inserts the asset, and only then constructs its success reply. The explicit comment at the conversion boundary says success must not leave the stored asset dependent on a producer-owned reference. Although `KittyAssetData::External` and lazy materialization helpers still exist, the current parser's `into_asset_data` returns `Image` for every accepted path. Copying the enum alone would miss this ownership decision. [Input media parsing](../../zellij/zellij-server/src/panes/kitty.rs:281), [finalization](../../zellij/zellij-server/src/panes/kitty.rs:646), [ownership boundary](../../zellij/zellij-server/src/panes/kitty.rs:2145).

Retained PNG assets contain the original PNG bytes after any Kitty transport zlib decompression. RGB/RGBA contain raw pixels. PNG dimensions come from signature/IHDR parsing; this is not a full PNG validation or decoding pass. Output can resend `f=100` without decoding/re-encoding. This supports choosing an encoded representation independently from any decoded pixels a renderer needs. [Conversion](../../zellij/zellij-server/src/panes/kitty.rs:2188), [PNG inspection and transmission](../../zellij/zellij-server/src/panes/kitty.rs:2676).

Input cleanup happens after a successful read, even if later image validation fails. Regular files remain producer-owned. Temporary files are removed only when their path contains `tty-graphics-protocol` and their canonical parent falls under a recognized temporary directory. Shared-memory inputs are opened read-only, copied, unmapped, and unlinked. Reads honor byte ranges. This makes temporary input cleanup distinct from acceptance of valid image contents. [External media ownership](../../zellij/zellij-server/src/panes/kitty_asset_store.rs:58), [file/range and path handling](../../zellij/zellij-server/src/panes/kitty_asset_store.rs:273), [shared memory](../../zellij/zellij-server/src/panes/kitty_asset_store.rs:339).

Existing tests exercise deleting a regular input file immediately after `OK` and still retrieving the stored bytes, temporary-file deletion after invalid PNG reads, shared-memory unlink before success, and unaligned/page offsets. Those are useful cleat contract scenarios. [Regular-file independence](../../zellij/zellij-server/src/panes/kitty.rs:3189), [temporary-file failure cleanup](../../zellij/zellij-server/src/panes/kitty.rs:3538), [shared-memory acceptance](../../zellij/zellij-server/src/panes/kitty.rs:3567).

## Asset identity and retention

The asset store owns internal image IDs and generations. Replacing an asset increments its generation; placements and the producer's protocol references remain separate concerns. The store tracks placement reference counts, insertion order, and a decoded-size quota of 320 MiB. PNG quota accounting uses width × height × 4 despite retaining encoded bytes. Eviction skips the newest asset, protected IDs, and assets with placement references. Therefore the quota is a pressure policy, not a hard memory bound: protected/referenced images can keep the store over quota. [Store and accounting](../../zellij/zellij-server/src/panes/kitty_asset_store.rs:443), [insertion](../../zellij/zellij-server/src/panes/kitty_asset_store.rs:511), [eviction](../../zellij/zellij-server/src/panes/kitty_asset_store.rs:617).

A client scene records resident asset generations separately from explicit/placeholder placements. Its diff can upload an asset independently of placing or deleting it. Resetting terminal state reconstructs residency from the required scene. This is a useful contract for reconnect and independent views; asset presence in the daemon does not imply presence in any client. [Scene types](../../zellij/zellij-server/src/output/kitty_diff.rs:33), [resident-state update](../../zellij/zellij-server/src/output/image_output.rs:628), [reset detection](../../zellij/zellij-server/src/output/image_output.rs:111).

## Client delivery and cleanup

Output transport selection is per client. The serializer tries configured regular-file, temporary-file, and shared-memory transports and falls back to direct bytes when they fail. Those output files are generated from retained assets; they are not forwarded producer paths. Regular output files are keyed by `(image_id, generation)` and reusable across clients. Temporary files and shared-memory objects are created per upload and tracked with client, asset, and generation, so one terminal's destructive read cannot consume another terminal's only copy. [Transport selection](../../zellij/zellij-server/src/output/image_output.rs:763), [output file cache](../../zellij/zellij-server/src/output/kitty_output_media.rs:105), [one-shot outputs](../../zellij/zellij-server/src/output/kitty_output_media.rs:139).

The output cache tracks pending uploads per client. Acknowledgement policy is none, every upload, or an ordered watermark: the final tracked upload requests a reply, which retires pending entries up to that point. The pending queue includes asset generation, but the terminal response matches by image ID. Responses, including errors, release the pending transfer hold; they are not proof that rendering succeeded. [Policy](../../zellij/zellij-server/src/output/image_output.rs:28), [queue and acknowledgement](../../zellij/zellij-server/src/output/kitty_output_media.rs:315), [response handling](../../zellij/zellij-server/src/screen.rs:3024).

Regular file retention takes the union of resident asset generations across connected regular clients and watchers, plus pending uploads, plus an optional recent-use grace period. One-shot files/shm are retained until their upload hold clears and retention policy allows cleanup. Disconnect removes that client's pending uploads. Session shutdown has explicit cleanup. These mechanisms work for one client and multiple clients without delegating retained asset ownership to the last viewer. [Retention policy](../../zellij/zellij-server/src/screen.rs:2975), [cache retention](../../zellij/zellij-server/src/output/kitty_output_media.rs:201), [disconnect](../../zellij/zellij-server/src/screen.rs:3935), [shutdown cleanup](../../zellij/zellij-server/src/screen.rs:8288).

The grace period is 240 render generations and the pending acknowledgement timeout is 960 render generations, not elapsed time. One-shot cleanup scans ordered queue heads. Consequently idle rendering can retain resources indefinitely and an older pending transfer can delay cleanup of later ones. These are code-derived tradeoffs to reconsider for cleat rather than copy by default. [Constants](../../zellij/zellij-server/src/output/kitty_output_media.rs:11), [queue reaping and expiration](../../zellij/zellij-server/src/output/kitty_output_media.rs:236).

## Recommendations for cleat

These are design recommendations inferred from the inspected code, not existing cleat behavior:

- Define successful producer acceptance as daemon ownership of reusable content. Capture external bytes before emitting success, including when no viewer is attached. Do not retain producer filenames/shm names as the replay source.
- Keep content identity/version separate from representation and per-client delivery. Permit PNG plus raw RGB/RGBA representations; do not force every retained asset through RGBA unless cleat's terminal engine requires it.
- Start daemon-to-client delivery with owned bytes and explicit asset generation. File/shm output is a later terminal-side optimization requiring local capability checks and separate cleanup. Wheelhouse need not implement terminal transport choices to consume retained assets.
- Keep per-attachment residency and placement state. Panning/history should change visible placements without replacing retained image bytes. Zellij's clipping code is additional prior art for adjusting source rectangles and assigning stable IDs to split fragments. [Fragment geometry](../../zellij/zellij-server/src/output/image_fragment.rs:49).
- Distinguish received bytes, terminal upload completion, and successful display. Make retries/reset behavior explicit instead of treating an emitted command or error response as confirmed terminal residency.
- Budget retained encoded bytes, possible decoded working memory, and in-flight transfers separately. Decide what happens when referenced history exceeds the budget; Zellij's soft decoded-size quota does not settle that question.

No other-project change is required to reuse these design lessons. The first cross-project work should test contracts: producer deletes external source immediately after acceptance; a second client attaches later; replacement uses a new generation; an older historical placement remains meaningful; one client's detach or cleanup cannot invalidate another's image.
